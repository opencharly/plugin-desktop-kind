# 2026.314.1306 — refactor(schema): derive the desktop-kind word sets from vocabulary tables

## Summary

Convert the five inline `|` word unions in
`candy/plugin-desktop-kind/schema/desktop.cue` to the §10.1 S3 vocabulary-table
idiom, so each closed set of words has ONE home and the enum an author meets is
`or()` of that table's keys:

```
_syntax  _manager  _numlock  _placement  _category
(+ _syntaxWord / _managerWord / _numlockWord / _placementWord / _categoryWord)
```

That is the 7 `union` rows `design/dpat-baseline.tsv` records for
`plugin-desktop-kind/candy/plugin-desktop-kind/schema/desktop.cue`. **They are FIVE
disjunctions, not seven:** `syntax`, `manager`, `numlock` and `placement` are each
written on one line (one row each), and `#DkCategory` is a 13-word catalog written
across three lines, each ending in `|` — three rows, one set. A union's row count is
a property of its formatting, so the row number is the only honest way to compare
repos and it is not a count of disjunctions.

**Plant 6 is the one this PR had to grow a test for, and it is worth naming.** It
restores `numlock?: *"none" | "on" | "off"` while LEAVING the `_numlock` table in place:
the field accepts exactly the table's three words, so every set- and probe-based check
passes — "the enum is derived" is not an equality property, and a runtime test cannot
see a table nothing cites by comparing sets. `TestEnumsFollowTheirTables` makes it
observable by MUTATING the table instead: a top-level `_x` struct is open, so a second
declaration of the same label adds a row, the comprehension recomputes, and the enum an
author meets must then accept the injected word. An enum that cites the derivation
follows; a hand-written one does not. Plant 6 came back GREEN before that test existed
and is RED after it, which is why the plant is kept in the battery.
